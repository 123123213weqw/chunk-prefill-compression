# v7：压缩 chunk 数量与顺序扫描

RTX4080真实运行 **228/228** 原子单元，约19分11秒，GPU任务退出；原Full/全压缩回答逐token精确复现，identity gate、旧引擎等价、层形状及原始记录审计通过。队列运行前冻结，完全跑完，不因中途错误提前停止。

实验仍使用**已经看过答案的**3个原v5失败样本和3个正确对照，全部 narrative/16K；这是机制扫描，不是新验证集准确率。

## 扫描方法

每份文档的T部分共256个64-token chunk。在第30层，被选中的chunk从64压到16个表示；其他chunk保持64。数量扫描为 **0、16、32、64、96、128、160、192、224、240、256**。按从前往后、从后往前和两组独立固定随机顺序逐步加入压缩chunk。顺序只用索引和固定随机种子，**不查看问题或答案**；但案例本身仍是事后选出的原失败样本。0和256端点四条轨迹共用，不能重复算成独立试验。

## 三个原失败案例首次答错的扫描点

| 样本 | 前→后 | 后→前 | 随机A | 随机B |
|---|---:|---:|---:|---:|
| `1155f1c2` | 224 | 256 | 224 | 256 |
| `18c56653` | **64** | **256** | 192 | 224 |
| `3615d039` | 256 | 256 | 256 | 256 |

- 第二个案例的顺序差异最大：前64个chunk被压就错；反向压到240个chunk仍对。因而**只看压缩比例，无法预测这道题是否保真**。
- 同一个案例的随机A首次出错在192个chunk，**仓库原始证据chunk尚未压缩**；前缀顺序在64个出错时，箱数证据chunk尚未压缩。这进一步否定“错误必须是答案所在chunk被压”的单一解释。
- 3个原失败样本×4条顺序，共12条轨迹；在已测的离散点中均只发生一次从正确到错误的翻转，**没有观测到错后恢复**。这不证明点与点之间或其他样本上数学单调。
- 3个正确对照×4条顺序，共12条轨迹，在已测点均正确。对照数量太少，不能推出通用保真率。
- 首次出错的数值只是本次**网格上的点**，不是精确临界值。比如首次在64个错，只知道32个仍对、64个已错；可用新实验细扫，但不能把未跑的点写成结果。

**结论：** 不仅压缩多少，**压哪一段**也决定结果；错题来自多处表示改变的组合效应，不能由向量平均/原始证据所在chunk单独解释。当前未得到不看答案就能可靠选择chunk的算法。
